Architecture documentation · v1.0

Real-time fraud detection,
built as six independent services.

PayGuard scores every merchant transaction in real time, approves / flags / blocks it in under 200ms, and keeps a full audit trail — from the charge to the settlement match.

Database per service

Every service owns its data. No shared schemas, no cross-service joins — Postgres per service, Redis added only where the Fraud Engine needs sub-millisecond feature lookups.

Sync only where latency is the point

The single hard synchronous dependency in the platform is Payment → Fraud Engine. Everything else — alerts, reconciliation, reporting — flows through Kafka.

Python trains, Java serves

Model development happens in Python. Real-time inference happens in the JVM via ONNX Runtime, with a rule-based fallback if the model can't answer in time.

06 · Security

Trust boundaries

AUTH

OAuth2 / JWT

User Service issues tokens; every service validates them independently via Spring Security. RBAC enforced per endpoint.

PCI

Card data never lands here

Stripe.js tokenizes on the client. Payment Service only ever sees Stripe tokens and charge IDs via the Stripe Java SDK.

WEBHOOK

Signature verification

Every inbound Stripe webhook is signature-checked before it's processed — no unverified event mutates state.

TRANSPORT

mTLS in-cluster

The Payment → Fraud Engine synchronous call runs over mTLS inside the EKS cluster.

SECRETS

Never in source

AWS Secrets Manager / Kubernetes secrets, provisioned by Terraform.

TENANCY

Scoped by merchant_id

Every table, cache key, and Kafka partition key carries merchant_id for isolation.

07 · Deployment

Infrastructure, provisioned as code.

08 · Operational notes

Non-functional considerations

LATENCY

Sub-200ms fraud check

Hard timeout on Payment → Fraud Engine, with a rule-based fallback rather than a silent hang.

RESILIENCE

Circuit breakers

Resilience4j around the Fraud Engine call; ONNX inference itself falls back to the rules engine on model failure.

GOVERNANCE

Model versioning

Every ONNX version is tagged and logged against the transaction it scored — enables rollback and audit.

IDEMPOTENCY

At-least-once delivery

Stripe webhook handling and Kafka consumers are built idempotent by design.

SCALING

Independent per service

Fraud Engine and Payment Service scale on latency/queue depth; they sit on the critical path.

OBSERVABILITY

Trace the sync path

Distributed tracing across Gateway → Payment → Fraud Engine attributes latency to a specific hop.
